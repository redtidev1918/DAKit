# Development, Building, and Releasing

## Pinned Toolchain

Current baseline:

```text
Flutter 3.47.1 stable (framework 6655482ec0)
Engine 5d53178869
Dart 3.13.1
```

GitHub Actions uses the same Flutter version. When upgrading the toolchain, update CI, `.metadata`, the native projects, and this document in a single commit, and re-verify all three platforms.

## Repository Structure

```text
packages/dakit_core/       platform-agnostic domain package
packages/dakit_api/        Dart OAuth/HTTP package
packages/dakit_web/        Flutter-free web-protocol adapter package
packages/dakit_flutter/    Flutter platform adapter package
packages/dakit_cli/        pure Dart command-line client
apps/example_client/       three-platform integration client
tool/verify.sh             quality gate shared by local and CI
```

The root `pubspec.yaml` manages the Dart workspace and the single lockfile. Library packages must keep their README, CHANGELOG, LICENSE, pubspec, and example to satisfy the publish checks. The Flutter native runners and `.metadata` are build/migration inputs, not disposable templates.

## Daily Verification

```shell
dart pub get
./tool/verify.sh
```

`tool/verify.sh` first pulls dependencies, then uses melos to run formatting,
static analysis, and the core, api, web, CLI, and example-app tests.

Finer-grained melos commands:

```shell
dart run melos run format
dart run melos run analyze
dart run melos run test
dart run melos run test:coverage
dart run melos run graph
dart run melos run doc
dart run melos run publish:check
```

`doc` generates the API documentation for the public packages into `docs/api/<package>/`. That directory is generated by a script and is not committed to Git; before releasing, use `dart run melos run doc` to verify that each package generates documentation with 0 warnings / 0 errors. It is pure build output: you can delete it any time (e.g. `rm -rf docs/api`) and regenerate it on demand.

Real OAuth/API tests are not part of the regular CI, because they require user authorization and are affected by provider content. See [LIVE_TESTING.md](LIVE_TESTING.md) for the testing approach.

## Platform Builds

Android requires JDK 17, Android API/Build Tools 36, and NDK `28.2.13676358`:

```shell
cd apps/example_client
flutter build apk --debug
```

macOS requires Xcode:

```shell
cd apps/example_client
flutter build macos --debug
```

Windows requires the corresponding Flutter/Visual Studio toolchain. Only MSIX registers the OAuth scheme:

```powershell
cd apps/example_client
flutter build windows --release
dart run msix:create --build-windows false --install-certificate false
```

These are all integration smoke builds, not store release packages. For formal distribution, the host application provides its own bundle/package identity, signing, icons, privacy statement, and store metadata.

## CI

`.github/workflows/ci.yml` runs on push, pull request, and manual triggers:

- Ubuntu: formatting, analysis, and the full test suite;
- Ubuntu: generate and upload `coverage/lcov.info`;
- Ubuntu/Android: debug APK;
- macOS: debug `.app`;
- Windows: release runner and a development MSIX with the `dakit` protocol;
- each platform uploads a smoke artifact.

Platform jobs depend on the quality job, and a new run on the same branch cancels the previous run. The regular pipeline does not store client IDs, secrets, tokens, proxy passwords, or signing credentials.

The Release workflow / ReleaseGraph builds standalone Linux x64/ARM64, Windows
x64, and macOS Intel/Apple Silicon CLIs. Native targets run version smoke tests;
the cross-compiled Linux ARM64 target validates its ELF architecture. The
workflow then creates `SHA256SUMS` and publishes a GitHub Release. macOS CLI
assets remain explicitly marked as unsigned previews until signing and
notarization are configured.

## Package Publish Checks

Run from a clean commit:

```shell
dart pub publish --dry-run --directory packages/dakit_core
dart pub publish --dry-run --directory packages/dakit_api
dart pub publish --dry-run --directory packages/dakit_web
flutter pub publish --dry-run --directory packages/dakit_flutter
```

The publish order is core → api → web → flutter. Before a formal release, confirm the
repository links, version dependencies, and changelogs. `dakit_core`/`dakit_api`
are 1.1.0 and `dakit_web` is 0.2.1; see
[RELEASING.md](RELEASING.md) for the full workflow.

## Commit Discipline

- Keep each milestone buildable and update [STATUS.md](STATUS.md) in the same commit;
- Do not commit `.dart_tool`, `build`, IDE state, proxy configuration, tokens, or real service reports;
- Do not hand-edit the generated plugin registrant; after upgrading plugins, regenerate it with the Flutter tool and verify;
- Public API changes must add tests and a changelog entry;
- For new endpoints, define the core contract first, then implement the api mapping; do not let DTOs reach the UI.
