# 三客户端生态的共同契约

状态：设计草案，2026-10-13。DAViewer、DeviantDrop、deviantart-downloader 的
已发布行为作为输入；本文不表示新的公共 API、跨语言 SDK 或客户端迁移已经完成。

## 目标与边界

把可复用的协议知识、判定规则、领域模型和回归证据集中维护。应用继续负责自己的
界面、Telegram 投递和批量归档。DAKit 是已有的 Dart SDK，也是语言无关契约和
脱敏样本的维护入口；Node/Python 保留原生适配器，不通过 Dart 子进程调用 SDK。

| 来源 | 已有优点 | 可共享部分 | 宿主保留部分 |
|---|---|---|---|
| DAViewer | 恢复协调、账号 epoch、请求所有权、跨启动诊断 | 身份/能力分离、迟到结果隔离、请求生命周期规则 | WebView、路由、Provider、推荐 UI 与缓存策略 |
| DeviantDrop | 原子凭据快照、Cookie 轮换、媒体归一化、发送前检查 | 安全存储语义、媒体角色、重试/投递边界 | Telegram 消息、限额、压缩、回复与取消策略 |
| Python 下载器 | Provider 与下载器边界、批量归档和错误提示 | 解析结果契约、错误分类、恢复检查点原则 | CLI、路径模板、SQLite 档案和文件下载调度 |

## 分层

```text
真实响应 / 权威协议资料
        ↓
脱敏协议样本与来源记录                 ← 三种语言共同使用
        ↓
原生协议适配器（Dart / Node / Python）
        ↓
Evidence → 纯判定规则 → 身份、能力、媒体结果
        ↓
宿主协调器 → UI / Telegram / 批量下载
```

协议适配器只提取事实，不删除 Cookie、不操作路由、不决定 Telegram 回复。
纯判定规则不访问网络或存储。宿主负责取消、时间预算、持久化和用户交互。

## 第一优先级：会话与能力契约

建议各语言归一化以下语义，名称是设计建议，尚未新增公共类型：

| 对象 | 最少信息 | 不变量 |
|---|---|---|
| SessionEvidence | 来源、采样时间、文档/请求标识、登录声明、用户名、观察失败原因 | Cookie/CSRF 存在只说明材料存在，不证明登录 |
| IdentityVerdict | signed_in / anonymous / unknown、账号、原因、证据引用 | 无用户名的登录声明保持 unknown；网络/WAF/解析失败不是登出 |
| CapabilityVerdict | 能力名称、confirmed / denied / unverified、原因、证据引用 | OAuth 身份、Web 身份、推荐个性化、作品权限分别判断 |
| RequestContext | 逻辑操作 ID、物理请求 ID、触发原因、账号 epoch、终态 | 成功响应也必须经过所有权检查；丢弃必须记录原因 |

沿用已有 SDK Token/PKCE 事务隔离。网页只在会话对象内判断登录声明，不能用页面
任意位置的字符串匹配。证据无法确认时保留凭据；退出/撤销才走显式清理路径。
具备 Web 身份不代表具备某作品的下载权限，也不证明推荐已经个性化。

降级信号必须带置信范围：例如 vespa 游标的语义仍未经充分确认，不能升级为
账号失效事实或整批丢弃依据。展示、缓存和投递策略由宿主根据产品需要选择；
DAViewer 的疑似推荐横幅不能直接搬成机器人的“需要重新登录”通知。

## 第二优先级：解析与媒体契约

复用 `dakit_core` 已有 `MediaAsset`、`MediaRole`、`MediaAvailability` 和稳定 ID
规则，比较 Node/Python 的现有模型后再增加映射，不另造一套 Dart 领域模型。
共同语义应区分作品、预览、原图、附件、可播放视频和文本内容；封面不能冒充视频，
预览不能冒充可下载原图。权限与不完整内容分别表达，允许返回部分可用结果。

外部 DTO 字段、URL 模板、权限信号必须先取得独立证据。现有实现中的模糊 URL
或游标启发式不能因“多个项目都这么写”而被宣布为标准协议。

## 第三优先级：请求、存储与诊断

- 一次逻辑操作与实际 HTTP 尝试分开计数。协议重试需要显式契约，不能偷偷增加
  传输；重试只用于可重试的读取/解析，上传、消息发送和文件最终提交分别处理幂等。
- Single-flight 只合并等价且可共享的读操作。键至少考虑账号/epoch、操作、参数和
  必要的会话版本；不能把不同账号或有副作用的操作合并。
- 时间预算不等于取消底层 I/O。过期调用的写入/清理仍须有序且受代际检查保护，
  否则超时后的旧操作可能破坏新会话。
- 原子快照、账户边界和不恢复过时环境 seed 可共享；文件、Keychain 和 Flutter
  secure storage 的实现由平台适配器负责。Windows ACL 与 POSIX mode 分别验证。
- 诊断事件共享操作/请求/epoch/阶段/错误类别/接受或丢弃原因。Token、Cookie、
  授权参数和媒体签名 URL 默认脱敏；导出、保留周期和用户入口由宿主决定。

## 契约与联合验证

`protocol-contracts/` 保存语言无关的脱敏样本、来源和预期语义。首个样本是
2026-10-13 独立匿名首页抓取，不包含有效 CSRF/Cookie 或用户信息。
已登录、异常和竞争场景必须明确区分真实采集与基于真实结构的策略变体。
共享预期由证据和明确政策决定，不能由任一语言实现自动生成。

各语言的 adapter contract runner 对同一组样本输出归一化 verdict，再比较公共
预期。另保留原生单位测试和宿主集成测试：协议一致不等于路由、发送或下载成功。
契约使用显式版本、SHA 和样本 hash；CI 禁止跟随未经固定的 latest 样本。

## 增量实施顺序

1. 本次落盘：职责边界与共同契约草案、首个脱敏样本及预期；不改运行时依赖。
2. 提取 DAKit Web 身份证据解析与纯判定接口，DAViewer 改为调用上游；同时让
   Node/Python 测试消费同一份固定版本契约，保留原生实现与现有行为。
3. 优先迁移已经有独立证据的解析字段和错误类别，再统一媒体映射与请求追踪字段。
4. 对三客户端完成合同测试、宿主回归和实际发布产物验证后，发布需要的 SDK/契约
   版本，再更新依赖。兼容变更与破坏变更分别评估，不同时重写三个应用。

暂不新增中心认证服务，不集中收集用户 Cookie，不把 Telegram/Flutter/CLI 的
宿主流程上移到 SDK，也不为统一语言而改写客户端。真实账号与原手机验收缺口
继续如实记录；不作为未经证实的架构成功结论。
